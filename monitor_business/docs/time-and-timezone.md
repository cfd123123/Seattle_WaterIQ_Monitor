# 时间与多时区：决策说明（业界常见做法 & 本项目现状）

面向 **`createdAt` / `createTime`**、告警列表筛选 **`createdFrom` / `createdTo`**、以及 JSON 里带时间戳的接口。若你暂时不熟悉这一块，可按下面顺序理解：**存什么、传什么、谁负责换算**。

---

## 1. 为什么要单独说「时间」？

同一时刻在地球上不同地区日历钟点不同。若 API 只写 `2026-03-30T10:00:00` **不带时区**，不同系统会按**各自默认时区**理解，容易出现：

- 筛选区间「少一天 / 多一天」；
- 同一笔数据在前端与库里「对不上」；
- 分布式日志、跨区运维对不齐。

业界目标通常是：**内部有一个统一标尺**（几乎都是 **UTC**），再在前端或展示层按用户时区渲染。

---

## 2. 业界常见做法（摘要）

### 2.1 API 与序列化（最常见、跨系统首选）

- **请求/响应体里使用时间**：多用 **ISO-8601**，并带 **偏移或 `Z`（UTC）**  
  - 例：`2026-03-30T02:56:38.548940Z`、`2026-03-29T19:56:38-07:00`
- **服务端存储**：常见为 **UTC 的瞬时时间**  
  - 数据库类型：`timestamptz`（PostgreSQL）、或与 ORM 约定统一用 **Instant / OffsetDateTime** 落到 UTC。
- **由谁做本地化**：**前端 / BFF** 按用户时区格式化成「本地可读字符串」；**后端**尽量不在业务核心层硬编码「北京时间」之类。

**代表形态**：REST/JSON 全链路 **UTC + ISO-8601**，文档里写清楚：「所有时间均为 UTC」。

### 2.2 「单区域」政务 / 企业内部系统（也常见）

- 业务只在一个国家/省份内，**约定「全系统使用一个标准时区」**（例如中国多用 **Asia/Shanghai**）。
- API 仍可带 `Z`（先转 UTC 再传）或带 `+08:00`；也有团队为省事使用 **无偏移的「当地挂钟时间」**，但必须在文档中**写死约定**，且**避免**跨国扩展。

### 2.3 仅日期、不含时分（报表日界）

- 用 **LocalDate** + 明确「按哪一时区的日历日切分」  
  例：`business_date` 表示「上海自然日」还是「UTC 自然日」，要在产品上明确，否则「日统计」会对不齐。

### 2.4 日志与链路

- **日志、Trace**：业界几乎统一用 **UTC**（或机器时间 + 记录时区），便于 ELK、Prometheus、跨区排障。

## 3. 本项目（monitor_business）当前实现

| 项目 | 现状 |
|------|------|
| **实体字段类型** | `LocalDateTime`（**无时区信息**） |
| **JPA / PostgreSQL** | `timestamp`（无时区的「挂钟时间」）；**不是** `timestamptz` |
| **JSON 序列化** | Spring Boot 默认对 `LocalDateTime` 常输出 **无时区的 ISO 字符串**（如 `2026-03-29T19:56:38.387358`） |
| **筛选参数** | `createdFrom` / `createdTo` 使用 **`@DateTimeFormat(iso = DATE_TIME)`**，绑定为 **`LocalDateTime`**，与库里比较为**同一条「无偏移时间轴」** |

**含义（重要）**：

- 可以把它理解成：**「服务器 / 数据库所在环境的挂钟时间」**，而不是「全球唯一的绝对时刻」除非你们全员约定这就是 `Asia/Shanghai`。
- **换一台不同时区的机器**或**库用 UTC 而应用用本地**，在没有显式转换时，**边界筛选可能漂移**。

这在「单机 + Docker PG + 本机开发」阶段通常**能接受**；若以后要 **SaaS 多地区** 或 **多地部署**，建议升级为 **UTC + `timestamptz` / Instant**。

---

## 4. 建议的演进方向（与业界对齐）

若产品要走向「标准、可扩展」：

1. **库表**：能改则优先 **PostgreSQL `timestamptz`**，存 **UTC**。  
2. **Java 模型**：新字段或新服务优先 **`Instant`** 或 **`OffsetDateTime`**；对外 JSON 用 **带 `Z` 的 ISO-8601**。  
3. **筛选接口**：接受 **`OffsetDateTime` 或 Instant**（字符串带 `Z`/`+08:00`），在服务端**统一转为 UTC** 再查库。  
4. **文档**：在 OpenAPI / `architecture.md` 中写明：**「时间均为 UTC」**或**「均为 Asia/Shanghai 挂钟时间」**（二选一，必须写死）。

---

## 5. 给前端 / 调用方的实操建议（在现状下）

在**仍使用 `LocalDateTime` + 无时区参数**的阶段：

- **同一部署环境里**：`createdFrom` / `createdTo` 请使用 **与应用服务器同一套挂钟** 的本地时间格式，例如 `2026-03-30T00:00:00`。  
- **跨环境对比数据**时：以 **数据库里实际存的值** 为准，不要盲目拿「UTC 日历」去拼字符串。  
- 需要**绝对时刻**时：优先让后端以后提供 **带 `Z` 的字段** 或单独文档约定时区。

---

## 6. 小结

| 做法 | 适用 |
|------|------|
| **API/DB 全面 UTC + ISO-8601（带 Z）** | 国际化、多区域、长期最省心（业界默认「正规军」） |
| **约定单一业务时区 + 文档写死** | 强地域系统、迁移成本低的阶段 |
| **当前项目：LocalDateTime + timestamp** | 开发期、单机部署；**升级前应书面约定**实际代表哪条「挂钟」 |

本文档随架构迭代更新；若完成 **UTC 改造**，应删除或重写 §3「当前实现」并更新 API 示例。
